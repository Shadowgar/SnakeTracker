# M6.5 Inventory Intelligence and Cost Tracking Architecture Proposal

Status: Proposed for owner review; no M6.5 implementation or migration has begun

Branch baseline: `8b0c062a39453bd2a4e65cb6ce288eea6298137f` (merged, owner-accepted M6)

Governing requirements: `R-070` through `R-076`

Decision record: [ADR-0042](../adr/0042-inventory-purchases-fifo-and-quantity-policy.md)

## 1. Existing-model audit

### Current Inventory semantics

| Concern | Current behavior | M6.5 disposition |
|---|---|---|
| Identity | UUID `Inventory Item` aggregate on `inventory-item:{uuid}` | Reuse unchanged |
| Quantity | Integer on-hand, reserved, consumed, and expired balances | Preserve v1; add scaled v2 quantity support |
| Unit | Required free-text unit stored on registration/update | Retain legacy text; constrain new use to one canonical unit |
| Receipt | `inventory.stock_received` v1 adds a positive integer quantity and optional reference | Preserve; add purchase-linked v2 |
| Adjustment | `inventory.stock_adjusted` v1 appends a nonzero integer delta and reason | Preserve; add structured reason/scaled v2 |
| Feeding link | Feeding and stock consumption append atomically; source feeding ID is projected | Reuse correlation and compensation behavior |
| Correction | Feeding correction reverses and replaces linked consumption atomically | Extend v2 handlers; do not redesign |
| Void/reinstate | Feeding void reverses stock; reinstatement consumes again | Reuse unchanged in meaning |
| Negative stock | Consumption, expiry, reservation, and adjustments fail if balance would be invalid | Retain |
| Archive | Archived items leave active selection and reject ordinary stock changes | Retain; allow authorized historical controls |
| Restore | Explicit event returns an archived item to active use | Reuse unchanged |
| History | Registration and all movements remain immutable; hard delete is unavailable | Reuse unchanged |
| Projection | `inventory_balance` is synchronous; consumption links/allocations support compensation | Evolve synchronously and retain links |
| Reports | No Inventory report; only Collection, effective Care history, and Expenses exist | Add read models and reports |

The current Inventory events are registration/update/archive/restore, receipt, reservation,
consumption/reversal, adjustment, expiry, and reorder-policy change. They correctly protect
current balance and household identity. They do not preserve a Purchase, vendor, paid amount,
cost lot, physical count, verification date, target/maximum, fractional quantity, usage rate, stock
duration, consumed value, or current value.

### Current Expense semantics

An Expense aggregate on `expense:{uuid}` owns positive integer minor-unit amount, three-letter
currency, category, payee, reference, occurrence time, notes, correction, and void state. Its
synchronous `expense_current` projection exposes active/void current facts and totals per currency.
It has no receipt lines, inventory receipt link, tax/fee breakdown, cost allocation, or
reinstatement. Expense reports list effective standalone Expenses only.

### Current feeding edge case

The stock-linked feeding path does not infer inventory use from outcome. If the keeper selects an
Inventory Item and quantity, stock is deducted whether the result is accepted, refused, or
regurgitated; without a selected item, no stock is deducted. This means the inventory fact is
"removed from available stock," not "eaten by the animal." M6.5 must preserve that qualified
meaning, make the choice explicit in the form, and never infer a deduction merely from a feeding
outcome.

## 2. Proposed domain concepts

- **Inventory Item:** remains the authority for identity, canonical unit, stock balance, lifecycle,
  item category, thresholds, verification policy, and movements.
- **Purchase:** new aggregate representing one paid receipt with one to 25 inventory lines. It is
  the authoritative cash-spend fact for that receipt.
- **Purchase line / receipt lot:** stable line identity connecting purchased quantity and allocated
  acquisition cost to exactly one Inventory Item and stock-receipt event.
- **Cost layer:** rebuildable read-side representation of a receipt or uncosted increase remaining
  under FIFO; not a mutable write aggregate.
- **Cost allocation:** rebuildable link from an effective depletion to one or more cost layers,
  classified as consumption, expiry, or variance.
- **Physical count:** immutable observed expected/actual fact on the Inventory Item stream. A shared
  workflow ID groups single-item saves made during a full or category count.
- **Inventory policy:** owner-set reorder minimum, optional target/maximum and lead time, plus
  optional recount interval. It contains no husbandry defaults.
- **Inventory intelligence:** derived, explainable usage, duration, verification, attention, and
  value facts. It owns no commands.

Purchase posting is an application service coordinating one Purchase stream and the distinct
Inventory Item streams through atomic multi-stream append. Purchase lines are not separate
aggregates. An item can have many immutable lots. Expense remains a peer aggregate only for
non-purchase spending.

## 3. Proposed events

These are the smallest additions that preserve typed meaning. "v2" denotes another registered
schema for an existing event type, not an in-place change to v1.

| Event contract | Stream | Factual meaning | Correction/void | Projection impact |
|---|---|---|---|---|
| `purchase.recorded` v1 | `purchase:{id}` | Records one posted receipt, vendor, currency, totals, and stable inventory lines | Correctable; generic void/reinstate permitted with receipt compensation | Purchase current/lines, cash spend, lots, reports |
| `purchase.corrected` v1 | Purchase | Full replacement of effective receipt facts targeting the root record | May itself be superseded; cross-stream receipt changes append atomically | Replaces effective Purchase and rebuilds affected cost items |
| `inventory.item_registered` v2 | Inventory Item | Adds owner-defined category while retaining canonical item unit | Registration is not voidable after use | Balance/intelligence/category views |
| `inventory.item_updated` v2 | Inventory Item | Changes name/category and, only before any movement, canonical unit | Later update supersedes configuration | Balance/intelligence |
| `inventory.stock_received` v2 | Inventory Item | Adds scaled quantity and optional typed Purchase/line source | Correctable and voidable; Purchase controls coordinate atomically | Balance, effective receipts, lots |
| `inventory.receipt_corrected` v1 | Inventory Item | Replaces the quantity of a targeted v2 receipt while preserving its Purchase/line source | Superseding correction; generic void applies to root receipt | Balance delta, lot rebuild, purchase reconciliation |
| `inventory.stock_consumed` v2 | Inventory Item | Removes scaled quantity for generic or linked use with structured kind/source | Existing reversal event compensates it; generic controls are not substituted | Balance, usage, FIFO allocation |
| `inventory.stock_adjusted` v2 | Inventory Item | Applies a scaled nonzero manual delta with structured reason and context | Compensated/corrected append-only; never mutated | Balance, uncosted layer or variance depletion |
| `inventory.stock_counted` v1 | Inventory Item | Records expected, actual, variance, context, and shared count workflow ID | Void plus replacement count; reinstatement only when valid | Balance, count history, last verified, lots |
| `inventory.reorder_policy_changed` v2 | Inventory Item | Sets minimum, optional target/maximum, and optional lead time | A later policy event supersedes it | Balance/intelligence/attention |
| `inventory.verification_policy_changed` v1 | Inventory Item | Sets or clears owner-selected recount interval | A later policy event supersedes it | Count-due intelligence |

Existing `event.voided`, `event.reinstated`, and `inventory.consumption_reversed` are reused. Existing
Expense events are unchanged. Version-1 Inventory contracts stay registered and replay exactly;
normalizers expose their integer quantities as exact thousandths to v2 projections.

Event payloads carry business facts only. Actor, household, occurred/recorded UTC times,
correlation, causation, idempotency, and typed subjects remain envelope concerns. Purchase and line
IDs become related subjects/typed fields only where their contract declares them; free-text
references never establish financial linkage.

## 4. Proposed projections and read models

### Synchronous correctness group

- **`inventory_balance` v2:** current scaled on-hand/reserved/consumed/expired quantity, canonical
  unit/category, active state, policies, last count, stream version, and compatibility fields.
- **`inventory_effective_receipts`:** root receipt, active correction/control state, Purchase/line
  source, and effective quantity needed to validate corrections and voids.
- **`purchase_current` / `purchase_line_current`:** effective Purchase lifecycle, totals, lines,
  linked receipt event IDs, and source versions.
- Existing consumption links/allocations continue to protect feeding compensation and are extended
  for v2 quantities.

These projections participate in the command transaction because authorization or stock validity
depends on them.

### Asynchronous generation groups

- **`inventory_costing`:** FIFO layers, per-depletion allocations, known/unknown quantities,
  consumed/expired/variance values, and current stock value per currency.
- **`inventory_intelligence`:** 30/90-day consumption, explainable rate, duration, last use/restock,
  last verification, count-due state, reorder state, and unused/excess observations.
- **`cash_spend_facts`:** one effective row per typed source (`expense` or `purchase`) with no
  duplicate Purchase-as-Expense row.
- **`inventory_report_facts`:** periodized item/category quantity and value facts plus provenance and
  freshness checkpoints.

These models use versioned generations and atomic activation under ADR-0008. A backdated or
corrected event schedules affected-item recalculation; a full rebuild remains deterministic.
Templates query public read models and never reconstruct accounting from raw payload JSON.

## 5. Purchase-to-Expense relationship

The recommended relationship is **Purchase is a specialized cash-spend fact**:

```text
Purchase aggregate ──projects once──> cash_spend_facts ──> Expenses view/reports
       │
       └──atomic receipt events──> Inventory Item streams

Expense aggregate ───projects once──> cash_spend_facts
```

Creating a Purchase does not create or require an Expense stream. Expenses displays two clearly
labeled sources: Supply purchases (links to Purchase) and Other expenses (links to Expense).
Technical uniqueness prevents one source from being projected twice. The generic Expense form
does not expose an Inventory/Purchase link and cannot claim the reserved purchase source kind.
Same-day/vendor/currency/amount similarity produces a duplicate warning, not a false hard failure,
because two real payments can match.

This is cleaner than coupled Purchase and Expense aggregates and preserves all existing Expenses.

## 6. Purchase lot and cost model

One Purchase models one real receipt and supports multiple lines. Each line records:

- stable `purchase_line_id`;
- same-household `inventory_item_id` and resulting receipt event ID;
- quantity in the item's canonical unit;
- line subtotal in integer minor currency units; and
- derived allocated acquisition cost.

The Purchase header records vendor, purchase time, currency, optional tax, fees, discount,
reference/note, and total paid. The invariant is:

```text
total paid = sum(line subtotals) + tax + fees - discount > 0
```

Tax/fee/discount net cost is allocated proportionally over positive line subtotals using integer
largest remainder with stable line-ID tie breaking. Resulting line costs sum exactly to total paid.
Lines become immutable cost lots; the item never receives a mutable price field. If a receipt
contains non-inventory spending, that portion is recorded separately as an Other Expense rather
than inventing a stock line.

## 7. Costing-policy comparison

| Criterion | FIFO | Weighted average |
|---|---|---|
| Normal-user explanation | "Oldest recorded stock is valued as used first" | "Every receipt changes the pool average" |
| Purchase-lot traceability | Preserved directly | Lots retained only as history, not remaining value basis |
| Implementation | Lot/allocation tables and exact remainder rules | Smaller current pool, but historical snapshots are still needed |
| Corrections/backdating | Reallocate affected item deterministically | Recompute every later average or freeze values inconsistently |
| Negative/count adjustment | Depletes identifiable oldest layers; positive variance is unknown cost | Unknown positive variance makes pool average misleading |
| Replay | Deterministic ordered effective facts | Deterministic only with exact average/remainder rules |
| Partial quantity | Cumulative proportional minor-unit allocation | Exact rational average and remainder tracking required |
| Unit compatibility | Requires one canonical unit | Also requires one canonical unit |
| Historical reporting | Explains which receipt costs were consumed/remain | Explains average but not which acquisition remains |

Both policies can be correct if fully specified. Weighted average is initially smaller but does not
remove the hard problems of corrections, unknown-cost variance, exact cents, or event-time order.

## 8. Recommended costing policy

Adopt FIFO as proposed in ADR-0042. It best satisfies purchase-history and explainability goals and
keeps changing prices visible. Order effective layers and depletions by business occurrence time,
then recorded time, global position, and event ID. Backdated corrections may legitimately revise
historical allocations; read models expose freshness while recalculation is pending.

For a partial allocation from a lot:

```text
allocation cost = floor(lot cost × new cumulative used / lot quantity)
                - floor(lot cost × prior cumulative used / lot quantity)
```

The final allocation therefore takes any remainder cent. Money stays integer minor units.
Currencies are never converted or added together; reports group values by currency.

## 10. Physical-count semantics

`inventory.stock_counted` records the projection's expected quantity and keeper-entered actual
quantity at command time. The domain validates `variance = actual - expected` and applies that
variance once. It records a fact even when variance is zero. Actor and time come from the event
envelope; an optional reason/note and shared workflow ID add context.

Count scopes are UI/application selections:

- **Single item:** open Count stock from item detail.
- **Category/subset:** select the active items in an owner category.
- **Full:** select every active item.
- **Rolling/cycle:** start with items whose owner-selected recount date is due.

Mobile Save & next appends each item count independently, then shows a review summary. This avoids
one huge cross-stream transaction. Concurrency conflict keeps the entered actual quantity, refreshes
expected quantity, and requires confirmation. A correction appends a void compensation plus a
replacement count; rows are never edited.

Using one enriched count event is preferable to count-plus-adjustment because expected, actual,
variance, verification, and balance effect are one observation with one idempotency boundary.
`stock_adjusted` remains for loss/damage, discovered receipts, and other non-count changes.

Verification labels are deterministic: no effective count is Not yet verified; a count with no
configured interval is `Verified <date>`; a count before its owner-selected due date is Verified
recently with that date; and a passed due date is Count overdue. No confidence score is calculated.

## 11. Reorder and target semantics

Policy belongs to the Inventory Item stream. The owner may set:

- reorder minimum;
- target quantity after purchase;
- optional maximum desired quantity;
- optional supplier lead time in days; and
- optional recount interval in days.

Constraints are `0 <= minimum <= target <= maximum` for values that exist. A minimum can exist
without target/maximum. `available = on hand - reserved`. An active item is Reorder now when
available is at or below minimum. It is Reorder soon only when a supported use rate predicts it
will reach minimum within the owner-entered lead time. Otherwise it is Stable or Not configured.
Archived items retain policy/history but never appear in attention/reorder actions.

Changing policy appends a new event; historical policy is not corrected in place. No species,
husbandry reference, or application default supplies a threshold.

## 12. Usage-rate calculations

Eligible use is effective, active `inventory.stock_consumed` v1/v2 after reversal/control
evaluation. It includes generic use and intentionally linked feeding use. Reservations, receipts,
expiry, manual adjustments, and count variance are excluded. Period boundaries use household-local
calendar days under ADR-0030.

For each item and as-of time, expose:

- exact quantity used in trailing 30 days;
- exact quantity used in trailing 90 days; and
- daily/weekly rate over `max(as-of - 90 days, item registration date)`.

A rate is supportable only with at least 28 observed calendar days, two distinct effective use
dates, and a positive used quantity in the half-open interval `[window start, as-of)`. Otherwise
display Not enough usage history. After 90 observed days with no use, display No recorded use in 90
days; do not show an infinite duration or pretend zero is a forecast. Corrections, reversals, voids,
and reinstatements recalculate the same effective set.

Trends display the actual 30-day rate beside the preceding 60-day rate when both are supportable.
They do not assign an opaque score or compare incompatible units.

## 13. Stock-duration calculations

When a usage rate is supportable and positive:

```text
estimated days remaining = available canonical quantity / recent daily rate
```

The calculation retains exact scaled quantities and rounds only for display. UI wording is
"About 3 weeks at your recorded 90-day rate," includes the window and as-of date, and never states
a guaranteed run-out date. Duration is unavailable when stock is reserved beyond availability,
history is insufficient, use is zero, the unit needs legacy review, or the analytical projection
is stale beyond its declared threshold.

Time to reorder minimum uses `(available - minimum) / daily rate`. Reorder-soon status additionally
requires the owner's lead time.

## 14. Overstock and unused presentation

Care Keeper reports observations, not verdicts:

- `Above your maximum by 12` only when the owner configured a maximum.
- `About 9 months at your recorded rate` when a rate is supportable.
- `No recorded use in 180 days` as a plainly stated fixed-window observation.
- `Usage history unavailable` for sparse or incompatible legacy facts.

The Overview may group these as Review stock, never as authoritative waste/overstock without the
owner's maximum. It does not infer species needs or recommend disposal.

## 15. Feeding-linked consumption treatment

The existing atomic Animal-plus-Inventory operation remains the model. New linked deductions use
scaled `inventory.stock_consumed` v2 and retain the feeding source event ID, correlation, causation,
typed Animal subject, and Inventory Item subject. FIFO allocation is derived; no lot ID is chosen by
the keeper.

The feeding outcome does not itself deduct stock. Selecting `Deduct from inventory` means the item
left available stock, including prey discarded after a refusal or regurgitation. A refused feeding
with no selected deduction consumes nothing. The UI must state that distinction and default the
deduction choice safely. If stock was returned, the keeper corrects the linked deduction.

Feeding correction reverses the active allocation and appends replacement use; void reverses it;
reinstate reapplies it. Those events remain atomic with the Animal control event. Effective replay
therefore gives the same quantity and consumption cost as live operation.

## 16. Generic consumption workflow

Use inventory is one neutral workflow for prey, substrate, bulbs, cleaning supplies, supplements,
and other categories. It captures item, canonical-unit quantity, occurred time, structured use kind
(`care`, `maintenance`, `discarded`, or `other`), optional related Animal or Enclosure, and note.
The domain validates same-household subjects and available stock, then appends one v2 consumption.

No category-specific aggregate or event is introduced. Corrections use the existing reverse-and-
replace pattern. Expiry and lost/damaged adjustments remain distinct because their value should not
be reported as ordinary consumption.

## 17. Units and conversion decision

An item has exactly one canonical stock unit. New items choose `each`, `count`, `package`, `g`,
`kg`, `oz`, `lb`, `mL`, or `L`; legacy custom unit labels remain readable. All movement forms show
that unit. Whole-item units accept integers; physical units accept at most three decimals. Domain
events and synchronous projections store integer thousandths, never binary floating point.

M6.5 does not convert package-to-each or between mass/volume units. A purchase line must be entered
in the item's canonical unit. Automatic conversion requires a later explicit conversion/rational-
ratio design. Unit change is prohibited after any stock movement. Historical unit-change streams
are flagged for keeper review; usage before the latest unit change is not combined silently.

## 18. Negative-stock policy

Retain the current prohibition. A command that would make on-hand negative or below reserved stock
fails atomically and offers Count stock, Record missing receipt, or Correct prior use. Purchase
correction/void follows the same rule. Cost projections may show unknown-cost quantity but never
invent a negative lot or negative value.

This is safer and more understandable than allowing debt-like stock, and it preserves current
qualified behavior.

## 19. Correction, void, and reinstate treatment

- **Purchase correction:** full replacement Purchase fact; monetary changes rebuild costs. Line
  additions receive stock, quantity changes append receipt correction, and removals void receipts
  atomically.
- **Purchase void:** generic Purchase control plus every active linked receipt control in one
  transaction; reject if stock invariants would fail.
- **Purchase reinstate:** append Purchase and receipt reinstatements atomically only if all are valid.
- **Receipt correction:** typed replacement of a root v2 receipt quantity; its Purchase/line source
  is immutable and relinking requires void plus a new receipt.
- **Consumption correction:** reverse active use and append replacement use. Cost allocations follow
  the effective replacement.
- **Consumption void/reinstate:** reversal/reapplication with original source lineage.
- **Count correction:** void the erroneous count effect and append a replacement count; do not edit
  expected/actual rows.

Historical controls remain possible for an archived item even though new ordinary movements are
not; otherwise archival would block financial correction. Every multi-stream operation uses all
expected versions, deterministic ordering, one idempotency result, and no partial commit.

## 20. Backward compatibility

- Every v1 Inventory and Expense event stays registered and unchanged.
- Existing integer quantities normalize exactly to thousandths.
- Existing receipts create uncosted lots; price is Unavailable, not zero.
- Existing uses remain valid and can consume uncosted layers under FIFO.
- Existing feeding links and compensations retain their source identity.
- Existing Expenses remain Other expenses; no heuristic converts or links them to Purchases.
- Existing reorder threshold becomes minimum; target, maximum, and lead time are Not configured.
- Last physical verification is Not yet verified until a count event exists.
- A legacy unit-change stream is marked Needs unit review and excludes incompatible earlier usage
  from rate/duration claims.
- Multiple currencies remain separately subtotalled; no historical exchange rate is fabricated.

## 21. Live-data migration strategy

No migration is part of this tranche. After ADR approval, M6.5-A may create the next expand-only
Alembic revision. It should:

1. create new Purchase, effective-receipt, costing, intelligence, and cash-spend tables;
2. add parallel scaled-quantity and policy fields while retaining legacy compatibility fields;
3. backfill current integer balance fields as exact `value * 1,000` values;
4. deploy dual-compatible readers/handlers before any v2 event can be written;
5. build and validate new projection generations from immutable events;
6. atomically activate compatible generations after FK/count/checksum validation; and
7. defer contract/removal work until a later compatibility window and approved migration.

The active paths must be resolved and protected before any future command capable of mutation.
Migration-from-zero, historical upgrade, rollback, replay, and restore qualification uses unique
temporary SQLite files/directories or copied snapshots outside active database and attachment
paths. Restores are never directed over the live database. Before/after live hashes/counts prove
qualification caused no business-data mutation.

## 22. Mobile and desktop UX information architecture

The interface extends accepted Care Keeper Design #2; this tranche implements none of it.

### Mobile Inventory Overview

```text
Inventory                         [Add purchase]
Needs attention
  3 reorder now · 2 counts due    [Review]
Stock snapshot
  Available items · known value · unknown-cost stock
Reorder soon
  item / amount left / owner minimum / duration
Verify stock
  overdue / not yet counted       [Start count]
Usage
  used in 30 days / shortest supported duration
Recent purchases
  vendor / date / total           [All]
All items                         [Search/filter]
```

Item cards prioritize actionable status, quantity/unit, owner minimum, last verified, and honest
rate/value availability. The warehouse-style list follows the decision support rather than leading.

### Item detail

Header: name/category/status and quantity. Sections: Needs attention, stock and policy, usage and
duration, verification history, Purchase/receipt history, consumed/current value, and immutable
movement history. Actions are Add purchase, Use inventory, Count stock, Adjust stock, Edit policy,
and Archive/Restore.

### Mobile count

```text
Start count -> choose Full / Category / Cycle / One item
item name + expected + large numeric actual input
[Back] [Save & next]
conflict refresh if expected changed
review saved variances and corrections
Finish -> summary and next due information
```

Controls remain 44×44 minimum, quantity input and primary action are thumb reachable, progress and
item unit remain visible, and scanning does not require entering each detail page. One item saves at
a time; a failed item does not lose completed counts.

### Desktop

Use the same hierarchy with attention/summary cards above a dense sortable table. Item detail may
place policy/quantity beside history/value. Purchase uses an accessible multi-line form with sticky
receipt totals. Count uses a table with persistent labels and a review pane. Desktop adds density,
not a different workflow.

### Expenses integration

Expenses groups Supply purchases and Other expenses, labels their source, links purchases to receipt
and item details, and displays totals per currency. It never offers a second editable Expense for a
Purchase.

## 23. Reporting model

### Per item

For an explicit period and currency, expose on-hand/available quantity, unit, reorder minimum,
last count expected/actual/time/actor, used quantity, 30/90-day totals, supported rate/duration,
purchased quantity/cash, consumption value, expiry/variance value, known stock value,
unknown-cost quantity, latest Purchase, usage observation, and source/freshness explanation.

Reconciliation is:

```text
effective received + positive adjustments
- consumption - expiry - negative adjustments = on hand

purchase acquisition value = consumption value + expiry/variance value
                           + remaining known value
                           (+ effects of active corrections)
```

Unknown-cost quantity is reconciled separately and never assigned zero value.

### Collection

Expose per-currency supply cash spending, other expenses, consumption value, expiry/variance value,
current known stock value, unknown-cost stock, reorder/count attention, unused observations,
category cash/consumption, and explainable potential replenishment.

A near-term supply-spend estimate is available only when an item has a supported use rate, owner
target/lead or selected horizon, and recent known acquisition cost. It reports the exact inputs and
uses the latest effective line cost as an estimate, not a quote or guarantee. Reports retain CSV
formula-injection protection and accessible tables for every visualization.

## 24. Security and household isolation

- Purchase, cost, count, and report data is household-private financial/business data.
- Application authorization resolves every direct ID and typed subject in the principal household.
- Multi-stream commands validate every Inventory Item and expected version before append.
- CSRF, session, role, idempotency, canonical command hash, bounded input, and security audit remain
  mandatory.
- Projection tables and joins include household ID; cross-household subject/source links are invalid.
- Reports/CSV query authorized read models, escape output, and do not reveal event/internal IDs.
- Purchase notes/references and financial values are excluded from unsafe logs and public search.
- M9 public profile/media routes cannot access these projections; public exposure is out of scope.
- Count/Purchase line counts, text, money, quantity, and date ranges are bounded to protect SQLite
  and the Raspberry Pi.

## 26. Qualification strategy

Required evidence maps directly to `AT-INVINT-01` through `AT-INVINT-06` and `AR-INVINT-01`:

- golden v1/v2 event fixtures, unknown-version fail-safe, replay and projection-generation tests;
- FIFO tables covering changing prices, shared charges, partial quantities, final-cent remainder,
  uncosted layers, backdating, correction/control, and per-currency separation;
- Purchase/receipt atomicity, idempotency, concurrency, 25-line bound, Expense uniqueness, and
  no-partial-failure tests;
- full/category/cycle/single counts, zero/positive/negative variance, concurrency, correction, last
  verification, and recurrence;
- generic and feeding-linked accepted/refused/regurgitated/corrected/voided/reinstated use;
- exact usage/duration/reorder/unused calculations including sparse, zero, stale, archived, and
  legacy-unit states;
- per-item/collection reconciliation, CSV, estimate labels, and asynchronous freshness;
- cross-household direct-ID/subject/projection/export denial, CSRF, roles, and private/public split;
- mobile 390×844 and desktop journeys, keyboard, screen-reader, zoom/reflow, and axe WCAG 2.2 AA;
- isolated zero-to-head and historical upgrade/downgrade/re-upgrade, rebuild/swap/rollback,
  backup/restore, FK/integrity, and resource/performance checks.

Every destructive target must be resolved, recorded, and proven distinct from active database,
attachment, backup, and runtime roots. No qualification user or fixture is created in live data.
Formal M7/M8 gates are not claimed by M6.5 evidence.

| Historical item unit changes are ambiguous | Flag for canonical-unit review/count; exclude incompatible earlier usage |
| Count saved item-by-item can be interrupted | Retain completed immutable counts and resume remaining selected items; do not claim all-or-none session completion |
| Same-looking legitimate payments exist | Warn on likely duplicate input but hard-unique only typed source identity/idempotency |
| Shared tax/fees allocation may surprise users | Explain allocated acquisition cost on Purchase/item detail; owner must approve ADR policy |
| Multiple currencies cannot be totaled honestly | Keep separate currency subtotals; defer exchange rates |
| Latest price is not a vendor quote | Label spending output as an estimate with source date and assumptions |
| Fixed thousandth precision may not cover a future unit | Reject unsupported precision; require a future versioned decision rather than rounding silently |
| Active live data could be harmed by qualification | Fail-safe path checks plus isolated files/copies/restores and before/after hashes are release blockers |

### Owner decision required now

Approve, amend, or reject ADR-0042's combined choice: bounded multi-line receipt Purchases as the
sole purchase cash-spend authority; capitalized shared receipt costs; FIFO; canonical units with
integer thousandths and no conversion; enriched item count facts; owner-controlled policies; and
strict nonnegative stock. No M6.5 implementation may start until this decision is recorded.
